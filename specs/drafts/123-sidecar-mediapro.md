# Plan #123: xifty-sidecar-mediapro adapter — MEDIAPRO.XML cross-clip lookup (revised)

## Problem
Sony XAVC SD cards ship a card-level index file at `PRIVATE/M4ROOT/MEDIAPRO.XML` cataloguing every clip on the card with cross-clip metadata (system kind, master version, media id, per-clip UMID, video/audio type, FPS, duration, aspect, thumbnail URI, and — on pro-cam variants — recording-session windows and cross-clip references such as "previous take" / "thumbnail of"). Unlike the per-clip NRT XML handled in #122, this sidecar is a single index file that lives several directories above the primary clip (e.g. primary at `…/M4ROOT/CLIP/C0242.MP4`, index at `…/M4ROOT/MEDIAPRO.XML`). The current `xifty-sidecar` framework expects co-located siblings; MEDIAPRO requires a bounded walk-up plus per-primary entry lookup. Real cards routinely contain orphan entries pointing at deleted clips, and cards may have been written by cameras whose clip is not listed at all — both must surface as info issues, never panic. Acceptance is grounded against the user's real fixture pair `fixtures/local/sony-mediapro-zv-e10.xml` (ZV-E10 card index, 477-line `MediaProfile` ver `2.10`, **consumer-camera shape — no `<RecordingSession>` and no cross-references**) and `fixtures/local/C0242M01.XML` (per-clip NRT whose UMID `060A2B340101010501010D4313000000EC112546461106C2DCFE23FFFE19CFEF` resolves to the `<Material uri="./CLIP/C0242.MP4">` entry at the tail of the MEDIAPRO file).

## Approach
Add a new workspace crate `xifty-sidecar-mediapro` mirroring the existing `xifty-sidecar-sony-nrt` adapter's shape (single `Sidecar` impl, `quick-xml` event-driven parsing, `MergePolicy::Complement`, `sidecar` container + `mediapro` namespace). Discovery walks parent directories upward from the primary path up to a bounded depth (4 hops) and stops at the first directory that contains `MEDIAPRO.XML` (case-insensitive); buffer-only callers (`primary_path = None`) return empty as the framework requires (`crates/xifty-sidecar/src/lib.rs:140-154`). Parsing is event-driven over the full document: capture the `<MediaProfile>` header (xmlns, version, createdAt), the `<Properties>/<System>` and `<Properties>/<Attached>` blocks, optionally a `<RecordingSession>` block under `<Properties>` (pro-cam only — absent on the ZV-E10 fixture), every `<Material>` entry's `uri`/`umid`/structural attrs, optional `<Reference>` cross-refs nested under matched `<Material>`, and at end-of-document emit (a) the present-clip's matched entry's fields under `mediapro.<tag>`, (b) a flat `media_profile.cross_refs.<i>.{kind,umid}` array reflecting any cross-references on the matched material, (c) a `media_profile.clip_count` summary derived from total `<Material>` count, (d) `media_profile.system_*`, `media_profile.media_*`, `media_profile.recording_session.{start,end}`, `media_profile.version` from the header blocks, and (e) `mediapro.thumbnail.path` resolved to an absolute path next to MEDIAPRO.XML. When the present clip is not listed, emit `sidecar_no_index_entry`. We do not pre-scan for orphans on every extract (that would walk the whole card on every clip); orphan reporting happens only for the matched clip's own `<RelevantInfo>` thumbnail when that file is missing on disk (`sidecar_target_missing`). The CLI wires it as the 5th adapter at `crates/xifty-cli/src/lib.rs:240-247`.

The session-cache hook called for in the issue is intentionally deferred. The `Sidecar` trait passes `bytes: &[u8]` per call, so caching MEDIAPRO.XML across primaries inside this crate would not cross-cut the framework's read step in `merge_into` (`crates/xifty-sidecar/src/lib.rs:166-185`) — the file is re-read by the framework. Adding cache plumbing to `SidecarRegistry` is a framework change that belongs in its own issue. This plan tracks that as an explicit follow-up risk and uses only single-clip semantics, which is enough to satisfy every other acceptance criterion.

Cross-check vs NRT: this adapter does not import `xifty-sidecar-sony-nrt`. The `umid` cross-check listed in the issue happens organically through the existing conflict detector once both adapters emit a `TargetMaterial.umidRef` (NRT) and `Material.umid` (MEDIAPRO) entry — they share namespace-distinct entries with comparable values, so disagreement is detected by the same path that already handles `quicktime`/`sony_nrt` overlap. No special handshake required.

Header / card-level (always emitted when source element is present):

| Source | Emitted entry | TypedValue |
|---|---|---|
| `MediaProfile@version` | `media_profile.version` | String |
| `MediaProfile@createdAt` | `media_profile.created_at` | String |
| `Properties/System@systemId` | `media_profile.system_id` | String |
| `Properties/System@systemKind` | `media_profile.system_kind` | String |
| `Properties/System@masterVersion` | `media_profile.master_version` | String |
| `Properties/Attached@mediaId` | `media_profile.media_id` | String |
| `Properties/Attached@mediaKind` | `media_profile.media_kind` | String |
| `Properties/Attached@mediaName` | `media_profile.media_name` | String (skip when empty) |
| `Properties/RecordingSession@startTime` (pro-cam) | `media_profile.recording_session.start` | String |
| `Properties/RecordingSession@endTime` (pro-cam) | `media_profile.recording_session.end` | String |
| count of `<Material>` | `media_profile.clip_count` | Integer (i64) |

Per-clip (matched `<Material>` only):

| Source | Emitted entry | TypedValue |
|---|---|---|
| `Material@umid` | `mediapro.umid` | String |
| `Material@videoType` | `mediapro.video_type` | String |
| `Material@audioType` | `mediapro.audio_type` | String |
| `Material@fps` | `mediapro.fps` | String |
| `Material@dur` | `mediapro.duration_frames` | Integer (i64) |
| `Material@ch` | `mediapro.channels` | Integer (i64) |
| `Material@aspectRatio` | `mediapro.aspect_ratio` | String |
| `Material/RelevantInfo[type="JPG"]@uri` | `mediapro.thumbnail.path` (absolute, resolved against MEDIAPRO dir) | String |

`<RecordingSession>` and `<Reference>` element names are inferred from the Sony pro metadata schema — they are NOT present in the ZV-E10 consumer fixture (confirmed: only `<MediaProfile>`, `<Properties>`, `<System>`, `<Attached>`, `<Contents>`, `<Material>`, `<RelevantInfo>` appear). The parser handles them when present and emits nothing when absent (no fabricated values). See Risks §1 and §3.

4. **MediaProfile parser — header + counts** — wire the `quick-xml` event loop (modeled on `parse_nrt`, `crates/xifty-sidecar-sony-nrt/src/lib.rs:155-503`). On `<System>` emit `media_profile.system_id`, `media_profile.system_kind`, `media_profile.master_version`. On `<Attached>` emit `media_profile.media_id`, `media_profile.media_kind`, `media_profile.media_name` (skip when empty). Do NOT collapse them. Verifiable: `parse_minimal.rs` unit test asserts both surface independently with their distinct values.

Emit `media_profile.recording_session.start` (String) and `media_profile.recording_session.end` (String). Element name and exact attribute names are inferred — the parser uses local-name match (`b"RecordingSession"`) and tries both attribute spellings, emitting only what is found. For the matched entry, emit `mediapro.umid`, `mediapro.video_type`, `mediapro.audio_type`, `mediapro.fps`, `mediapro.duration_frames` (Integer/i64), `mediapro.channels` (Integer/i64), `mediapro.aspect_ratio`. ## Risks
- **`<RecordingSession>` element name and attribute spelling are inferred, not observed in the available fixture.** The ZV-E10 consumer-cam fixture has no `<RecordingSession>` (confirmed: only `<MediaProfile>`, `<Properties>`, `<System>`, `<Attached>`, `<Contents>`, `<Material>`, `<RelevantInfo>` appear). The Sony pro metadata schema commonly uses `<RecordingSession>` with `startTime`/`endTime` attributes inside `<Properties>` on pro-cam variants (XAVC-S300, FX-series). The parser uses local-name element match and tries both `startTime`/`endTime` and `start`/`end` attribute spellings; it emits only what is found and emits nothing when absent. **This field is acceptable to be absent on consumer-cam fixtures; it will surface from pro-cam fixtures when one is added to `fixtures/local/`.** If a pro-cam fixture lands later and the actual element name differs (e.g. `<RecSession>`, `<Session>`), this is a one-line constant change in the parser. The handcrafted unit fixture in step 5 documents the assumed shape so the contract is explicit.
- **`<Reference>` cross-ref shape is inferred similarly.** The ZV-E10 fixture has zero cross-clip references. Sony pro schemas typically nest `<Reference type="..." umidRef="...">` inside either `<Material>` directly or `<Material>/<Component>`. The parser uses local-name match for both `Reference` and `Component` (passthrough) and tries both `type`/`kind` and `umidRef`/`umid` attribute spellings. **Field is acceptable to be absent on consumer-cam fixtures; will surface from pro-cam fixtures when available.** If a pro-cam fixture lands and the names differ, single-line constant changes resolve it. Common observed `kind` values in Sony pro metadata: `"thumbnail"`, `"previousTake"`, `"continuation"` — these appear in the handcrafted unit fixture.
- **Session cache hook deferred.** The issue calls for a `SidecarRegistry` session cache so MEDIAPRO.XML is parsed once per batch. The trait shape today re-reads `bytes` per call inside `merge_into` (`crates/xifty-sidecar/src/lib.rs:169`). Adding the cache cleanly is a separate framework change. This plan ships single-clip semantics only; batch performance is correct but not optimal. **Recommended follow-up issue: "SidecarRegistry session cache for index-style sidecars"**.
- **Primary-path-in-parse plumbing via `SidecarRef.label`.** The parser needs the primary clip's basename to do entry lookup. We encode it in `SidecarRef::label` (`MEDIAPRO|<basename>`) instead of changing `MergeContext` because `MergeContext` is a stable Phase-1 surface (currently a unit struct, `crates/xifty-sidecar/src/lib.rs:69-71`). The `|` split is the first operation in `parse` and produces a graceful `sidecar_no_index_entry` Info issue if the token is absent — never a panic or index-out-of-bounds.
- **Schema version `2.10` vs the `2.10+` claim in the issue.** The constant is the prefix `http://xmlns.sony.net/pro/metadata/mediaprofile` (URN, no version in the URN itself); the schema version comes through as `media_profile.version` from the `@version` attribute. Documented in a code comment.
- **Walk-up case sensitivity on FAT32 / case-insensitive mounts.** SD cards mounted on macOS are typically MS-DOS (FAT32) which is case-insensitive but case-preserving. We do a case-insensitive directory scan rather than `Path::join("MEDIAPRO.XML").exists()` so Linux/Windows behave identically.
- **Bounded depth = 4.** Real Sony layout is `M4ROOT/CLIP/C*.MP4` → `M4ROOT/MEDIAPRO.XML` (2 hops). 4 lets users mount the card under a wrapper directory or through a copied tree without recursing toward `/`.
- **Insta snapshot tests** are not added here because no snapshot crate consumes mediapro output yet; assertion-based tests cover the contract. If `xifty-cli` insta snapshots happen to include the new entries when run against a fixture clip, the `cargo insta review` policy applies (per SRS §3.6).
