# Plan #62: RAW — Canon CR2 (TIFF-based + xifty-meta-canon)

## Problem
CR2 is Canon's TIFF-shaped RAW format. Files start with the standard TIFF II*\0 header but additionally carry the bytes `CR\x02\x00` at offset 8 (where DNG would carry IFD0 offset 8 + DNGVersion tag). XIFty currently routes any TIFF-shaped buffer to either `Format::Tiff` or `Format::Dng` (via `is_dng_tiff` at `crates/xifty-detect/src/lib.rs:64-112`), with no `Format::Cr2` and no Canon MakerNote interpreter — even though Sony's MakerNote interpreter at `crates/xifty-meta-sony/src/lib.rs` is wired into the TIFF extract pipeline (`crates/xifty-cli/src/lib.rs:562-568`). We need detection, a Canon MakerNote namespace crate, and CLI/CAPABILITIES wiring, while explicitly shipping at `planned` (per the issue's reference to plan ambiguity #3 and parent issue #5).

## Approach
Mirror the Sony precedent end-to-end. Add a CR2 magic check ahead of the existing DNG check in `detect()`; the CR2 marker (`CR\x02\x00` at offset 8, after the IFD0 offset u32 at bytes 4..8 — note the offset 8 magic differs from IFD0 offset because CR2 violates strict TIFF and writes the marker at bytes 8-11, with IFD0 stored at bytes 12+ for some encoders; we will detect using the documented Canon signature: magic `0x4352` at byte 8 and `0x02` at byte 10). Add `Format::Cr2` to `xifty-core`. Reuse `parse_tiff` for IFD0 / EXIF IFD / GPS IFD walking — no new container crate is needed because TIFF parsing already exists. Create `xifty-meta-canon` modeled on `xifty-meta-sony`: signature `decode_from_tiff(bytes, base_offset, container_name, tiff, exif_entries) -> Vec<MetadataEntry>`, gated on EXIF `Make == "Canon"`, reading MakerNote tag `0x927C`, walking it as an IFD with the Canon header convention (no header bytes — Canon MakerNote is a plain IFD using the parent TIFF base offset). Wire `decode_canon_from_tiff` into `tiff_extract` for the `cr2` container label. Surface CR2 in `CAPABILITIES.json` under `containers.cr2` with the `canon` namespace at `planned` (structural parse only) per the issue's bounded-criteria ambiguity.

## Risks
- **CR2 magic placement**: the `CR\x02\x00` bytes overlap with what would be the IFD0 offset u32 in standard TIFF. Real CR2 files set IFD0 offset to `0x00000010` (16) at bytes 4..8 and place the Canon signature at bytes 8..12. We must check IFD0 offset is 0x10 AND bytes 8..12 == `CR\x02\x00` (LE) / `\x00\x02RC` (BE). Mis-detection could pull plain TIFFs into the CR2 path.
- **Detect ordering**: CR2 check must run before `is_dng_tiff` — DNG and CR2 are mutually exclusive but both are TIFF-shaped. Order tests explicitly cover this.
- **Canon MakerNote variants**: there are several Canon MakerNote header layouts (no-header for old bodies, footer-anchored offset bases for newer bodies, encrypted CameraInfo). For `planned` status we only walk the top-level IFD; do not attempt CameraInfo or encrypted blocks. Module doc must call this out.
- **Bounded scope is blocked on issue #5** — do not advance `canon` to `bounded` in CAPABILITIES until kstore tag list is settled. The acceptance criteria explicitly call this out.
- **No CR2 fixture exists** — synthetic fixture must be small and deterministic; if generating bytes inline in a test feels cleaner than committing a binary, prefer a hex-array `build_cr2_fixture()` helper inside the cli test module (mirrors `tiff_with_tag` at `xifty-detect/src/lib.rs:283`).
