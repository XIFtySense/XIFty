# Plan #135 (revised): Tier S — classic .THM JFIF thumbnails for older video (.mov / .avi / .mp4 / .mts)

## Problem
Older Canon, Nikon, Olympus, Pentax, Casio, Sony, and Panasonic camcorders write a `<basename>.THM` JFIF thumbnail next to every `.MOV` / `.AVI` / `.MP4` / `.MTS` clip. These files frequently carry the *only* rich EXIF (make/model/captured_at, sometimes GPS) the user has for archival video — the video container itself is often metadata-bare in the mid-2000s through ~2015 era. Wave 1's `xifty-sidecar-gopro` (PR #141) already handles GoPro's specific `GH/GX`-prefix `.THM` flavor; we now need a generic classic-`.THM` adapter that complements (does not duplicate or shadow) it, while strictly respecting the container/interpretation crate-boundary rule in `.loswf/config.yaml:53`.

## Approach
Add a new crate `xifty-sidecar-classic-thm` implementing `xifty_sidecar::Sidecar`. The crate depends ONLY on `xifty-core`, `xifty-sidecar`, and `xifty-container-jpeg` — exactly mirroring the dependency surface of `crates/xifty-sidecar-gopro/Cargo.toml:7-12` (no `xifty-container-tiff`, no `xifty-meta-exif`). It performs JFIF SOF dimension extraction inline (verbatim of the GoPro SOF walk at `crates/xifty-sidecar-gopro/src/lib.rs:223-285`) and, when an APP1 EXIF segment is present (`JpegContainer::exif_payload()` at `crates/xifty-container-jpeg/src/lib.rs:20-28`), emits the raw EXIF bytes as a single `MetadataEntry` `thumbnail.exif_payload` of `TypedValue::Bytes` (variant defined at `crates/xifty-core/src/lib.rs:131`). The CLI then dispatches that payload through the existing TIFF + EXIF decode chain at `crates/xifty-cli/src/lib.rs:262-283` and projects selected EXIF tags onto flat `thumbnail.exif.{make,model,captured_at}` fields under namespace `classic_thm`. Discovery is same-stem `.THM` (case-insensitive) next to `.mov` / `.avi` / `.mp4` / `.mts` primaries, with an exclusion of stems that GoPro's adapter currently claims (`^G[HX]\d+$`, matching `gopro_lrv_stem` at `crates/xifty-sidecar-gopro/src/lib.rs:175-191`). `GP`-prefix stems are NOT skipped here — the GoPro adapter does not claim them today, and skipping them would orphan those files; coverage for `GP` is a separate future issue. Priority is `50` (vs GoPro's `100`) for deterministic iteration order ONLY — `MergePolicy::Complement` does a plain `.extend()` at `crates/xifty-sidecar/src/lib.rs:201-204` and performs no deduplication, so the stem-skip is the SOLE collision-avoidance mechanism.

## New files
- `crates/xifty-sidecar-classic-thm/Cargo.toml` — package metadata; deps ONLY on `xifty-core`, `xifty-sidecar`, `xifty-container-jpeg`. No tiff/exif crates.
- `crates/xifty-sidecar-classic-thm/src/lib.rs` — `ClassicThmSidecar` impl: discovery + JFIF dimension walk + raw APP1 payload emission + provenance helpers + unit tests.

## Step-by-step
1. **Scaffold the crate.** Create `crates/xifty-sidecar-classic-thm/{Cargo.toml,src/lib.rs}` with `pub struct ClassicThmSidecar; impl ClassicThmSidecar { pub const fn new() -> Self { Self } }`. Cargo deps strictly: `xifty-core`, `xifty-sidecar`, `xifty-container-jpeg`. Register the crate in workspace `Cargo.toml` `members`. Outcome: `cargo check -p xifty-sidecar-classic-thm` succeeds; `cargo tree -p xifty-sidecar-classic-thm` shows no `xifty-container-tiff` or `xifty-meta-exif`.
2. **Implement discovery.** Port the directory-walk pattern from `xifty-sidecar-gopro/src/lib.rs:104-171`, restricted to: primary extension in `{mov, avi, mp4, mts}` (case-insensitive via `eq_ignore_ascii_case`), and one same-stem case-insensitive `.THM` sibling. Skip when `is_gopro_stem(stem)` returns true, where `is_gopro_stem` matches `^G[HX]\d+$` (case-insensitive on the leading two letters), exactly the coverage of `gopro_lrv_stem` at lines 175-191. Do NOT skip `GP` stems. Outcome: discovery returns at most one `SidecarRef { label: "thm" }`; returns empty for buffer-only callers, `GH/GX`-prefix stems, non-video primaries, and missing siblings; returns a hit for `GP010001.MOV` (so the file is not orphaned).
3. **Implement JFIF dimension extraction.** Reuse `xifty_container_jpeg::parse_bytes(bytes, 0)` and the SOF-segment walk verbatim from `xifty-sidecar-gopro/src/lib.rs:223-285` — same masking rule `(marker & 0xF0) == 0xC0 && !matches!(marker, 0xC4 | 0xC8 | 0xCC)` and same `[precision][height_be_u16][width_be_u16]` payload layout. Add a `// kept in sync with xifty-sidecar-gopro::parse_thm SOF walk` comment at the top of the function. Emit `thumbnail.path` (String), `thumbnail.size_bytes` (Integer), `thumbnail.format = "jfif"` (String), `thumbnail.dimensions.width` / `.height` (Integer). On parse failure or missing SOF, push `SIDECAR_PARSE_ERROR` (`Severity::Warning`) and still surface path + size_bytes. Outcome: malformed `.THM` does not break extraction.
4. **Emit raw APP1 payload as Bytes.** Call `JpegContainer::exif_payload()` on the parsed container; if `Some((base_offset, payload))`, push a single `MetadataEntry { namespace: "classic_thm", tag_id: "thumbnail.exif_payload", tag_name: "thumbnail.exif_payload", value: TypedValue::Bytes(payload.to_vec()), provenance: { container: "sidecar", namespace: "classic_thm", path: Some(sidecar.path.display().to_string()), offset_start: Some(base_offset), offset_end: Some(base_offset + payload.len() as u64), notes: vec![format!("classic thm app1 exif ({})", sidecar.label)] }, notes: vec![] }`. NO TIFF parsing, NO EXIF decoding inside the sidecar crate — this is the boundary-clean handoff. If no APP1 EXIF segment is present, emit no payload entry and no warning (pure-JFIF THMs are normal). Outcome: sidecar crate has zero awareness of EXIF tag semantics; raw bytes flow downstream.
5. **Wire trait + helpers.** Implement `Sidecar::name() = "classic_thm"`, `discover()` from step 2, `parse()` dispatching only on `LABEL_THM` (`"thm"`), `priority(): u8 = 50`, `merge_policy() = MergePolicy::Complement`. Reuse the `provenance` / `push_string` / `push_integer` helper shape from `xifty-sidecar-gopro/src/lib.rs:385-428`. The `priority: 50` value is documented in code with a comment: `// Sort order only — MergePolicy::Complement does a plain .extend(); the stem-skip in discover() is the sole de-duplication mechanism.`. Outcome: trait surface compiles and matches Wave 1 conventions.
6. **CLI projection of `thumbnail.exif_payload`.** In `crates/xifty-cli/src/lib.rs`, after `registry.merge_into(...)` populates `entries` (locate the call site by reading `extract_source()` end-to-end; merge happens after the format-specific extraction blocks), add a new helper `project_classic_thm_exif(entries: &mut Vec<MetadataEntry>, issues: &mut Vec<Issue>)` that: (a) scans `entries` for any `tag_id == "thumbnail.exif_payload"` && `namespace == "classic_thm"` && `value` is `TypedValue::Bytes`, (b) for each such entry, calls `xifty_container_tiff::parse_bytes(&bytes, offset_start.unwrap_or(0), "classic_thm_exif")` (push parse issues into `issues`), then `xifty_meta_exif::decode_from_tiff(&bytes, offset_start.unwrap_or(0), "sidecar", &tiff)`, (c) iterates the resulting `Vec<MetadataEntry>` and projects tag IDs `"0x010F"`, `"0x0110"`, `"0x9003"` (string format per `crates/xifty-meta-exif/src/lib.rs:60` — confirmed in prior review) into new entries with `namespace = "classic_thm"`, `tag_name`/`tag_id` set to `"thumbnail.exif.make"` / `"thumbnail.exif.model"` / `"thumbnail.exif.captured_at"`, value cloned from the decoded entry (`String` for make/model, `Timestamp` for captured_at), provenance `{ container: "sidecar", namespace: "classic_thm", notes: vec!["projected from classic .thm app1 exif"] }`, (d) removes the original `thumbnail.exif_payload` entry from `entries`. Note: `xifty-cli` already depends on both `xifty-container-tiff` and `xifty-meta-exif` (used at lines 262-266) so no new Cargo deps are required at the CLI layer — the EXIF dispatch crate-boundary is preserved exactly as for JPEG primary path. Outcome: `thumbnail.exif.make` / `.model` / `.captured_at` appear in CLI output for `.THM` files carrying APP1 EXIF; raw `thumbnail.exif_payload` is consumed and not surfaced.
7. **Register sidecar in CLI.** Add `use xifty_sidecar_classic_thm::ClassicThmSidecar;` to the imports of `xifty-cli/src/lib.rs` near line 25 and append `registry.register(ClassicThmSidecar::new());` to `default_sidecar_registry()` at line 246 after `C2paSidecar`. Add the path-dependency line to `crates/xifty-cli/Cargo.toml`. Outcome: CLI gains the 5th sidecar.
8. **Update `CAPABILITIES.json`.** Add a `classic_thm` block to the `sidecars` map with `status: "bounded"`, `merge_policy: "complement"`, `priority: 50`, `discovery: "same-stem .THM (case-insensitive) next to .mov/.avi/.mp4/.mts; skips GoPro GH/GX-prefix stems (matches gopro_lrv_stem)"`, and `supported_tags`: `thumbnail.path`, `thumbnail.size_bytes`, `thumbnail.format`, `thumbnail.dimensions.width`, `thumbnail.dimensions.height`, `thumbnail.exif.make`, `thumbnail.exif.model`, `thumbnail.exif.captured_at`. Add a `notes` field clarifying that the sidecar crate emits raw `thumbnail.exif_payload` (Bytes) and the CLI projects the flat `thumbnail.exif.*` fields via the existing TIFF + EXIF dispatch chain. Explicitly state that priority is sort order only and that the GH/GX stem-skip is the sole collision-avoidance mechanism with the GoPro adapter.

## Risks
- **GP-stem coverage gap**: until GoPro's adapter is extended to claim `GP\d+` stems (separate future issue), `GP010001.MOV + GP010001.THM` pairs will be claimed by classic-thm. This is the correct default — better one adapter surfacing data than zero. Documented in `CAPABILITIES.json` notes.
- **CLI projection ordering**: `project_classic_thm_exif()` must run AFTER `registry.merge_into(...)` so the raw `thumbnail.exif_payload` entry exists, and BEFORE any conflict detection / serialization that would treat the raw Bytes entry as user-facing output. Builder must place the call accordingly and verify with the integration test in step 6 / Tests.
- **EXIF tag-id projection**: projection matches on the string form `"0x010F"` / `"0x0110"` / `"0x9003"` per `crates/xifty-meta-exif/src/lib.rs:60` (`format!("0x{:04X}", entry.tag_id)`). Not on `tag_name`, which uses a static lookup with potentially divergent casing.
- **Namespace correction**: `xifty-meta-exif` hardcodes `namespace = "exif"` for entries it produces (`crates/xifty-meta-exif/src/lib.rs:30`). The CLI projection step explicitly sets the new entries' namespace to `"classic_thm"` — we are not reusing the original entries, just reading their `tag_id` and `value` and constructing fresh entries.
- **Priority is sort order only**: emphasised in code comments and `CAPABILITIES.json` notes; the stem-skip in `discover()` is what actually prevents `thumbnail.*` duplication when both adapters see the same `.THM` file. `MergePolicy::Complement` does no deduplication (`crates/xifty-sidecar/src/lib.rs:201-204`).
- **No real-world fixture in this PR**: a Canon/older `.MOV` + `.THM` pair would be ideal but is not blocking; synthetic fixtures cover the structural surface.
- **Case-insensitive stems on case-sensitive filesystems**: same trade-off as GoPro Wave 1; extension matched case-insensitively, stem matched exactly. Acceptable per established convention.
