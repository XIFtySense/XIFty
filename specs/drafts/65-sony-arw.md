# Plan #65: RAW — Sony ARW (TIFF-based, extends xifty-meta-sony)

## Problem
Sony ARW is a TIFF-based RAW format identified by standard TIFF magic plus EXIF `Make=SONY`. The repo already has `xifty-meta-sony` (`crates/xifty-meta-sony/src/lib.rs:1-99`) which decodes Sony MakerNote tags off any TIFF, plus a TIFF detector that already special-cases DNG (`crates/xifty-detect/src/lib.rs:10-15`). We need to add `Format::Arw` so ARW files are recognized distinctly from generic TIFF/DNG, dispatch them through the existing `tiff_extract` path (`crates/xifty-cli/src/lib.rs:541-625`) under an `arw` container label, document ARW-specific MakerNote tag coverage in `xifty-meta-sony`, and reflect support in `CAPABILITIES.json`. No FFI shape changes.

## Approach
Mirror the existing DNG branch end-to-end: DNG was added by extending the same TIFF detector with a tag probe (`is_dng_tiff` at `crates/xifty-detect/src/lib.rs:64-112`), routing through `parse_tiff` in both probe and extract dispatchers (`crates/xifty-cli/src/lib.rs:59-62, 217`), and using `tiff_extract` with a distinct container label. ARW follows the same shape but its detection key is `Make="SONY"` in IFD0 rather than a single tag presence — we walk IFD0 once for tag `0x010F` (Make) and string-match `SONY*`. We do **not** create a new container crate; ARW is exactly TIFF on the wire. The `xifty-meta-sony` crate already runs on every TIFF-shaped extract regardless of label (see `decode_sony_from_tiff` invocation at `crates/xifty-cli/src/lib.rs:562-568`), so it will fire for ARW automatically. Documentation of ARW-relevant MakerNote tags is added as module-level rustdoc on `xifty-meta-sony` — Acceptance Criterion only requires documenting ARW-specific coverage, not new tag decoders (Task 10 ambiguity #3 says canonical tag list is TBD). Snapshots use the local-fixture skip pattern (`crates/xifty-cli/tests/cli_contract.rs:61, 1215-1283`) since ARW files are large/proprietary and live in `fixtures/local/`.

## Risks
- **ARW MakerNote header differs from JPEG.** `xifty-meta-sony`'s gate (`SONY_MAKER_NOTE_HEADER = "SONY DSC \0\0\0"` at `crates/xifty-meta-sony/src/lib.rs:5`) was tuned for JPEG-resident Sony MakerNote. Many ARW MakerNotes have no header or use a different vendor prefix; with no local ARW, we cannot empirically confirm whether `decode_from_tiff` returns entries on a real ARW. Acceptance Criterion #2 says "main EXIF + sony maker-note surface" — main EXIF will surface unconditionally; the Sony decoder may surface zero entries against the synthetic fixture (which has no MakerNote tag). The plan keeps the header gate untouched to avoid regressing JPEG; documenting ARW-specific MakerNote semantics satisfies AC #3. If a builder discovers a real ARW locally and finds the header gate wrong, that's a follow-up issue, not in-scope here.
- **Make-tag detection edge cases.** Inline (≤4 bytes) vs out-of-line ASCII strings, missing NULs, mixed case ("Sony Corporation"). The probe must accept any Make that uppercases to start with "SONY" and bounds-check both inline and out-of-line reads, mirroring the defensiveness in `is_dng_tiff` (`crates/xifty-detect/src/lib.rs:64-112`).
- **DNG vs ARW priority.** A Sony-shot DNG would match both signals. Plan keeps DNG winning (DNG is a normalized superset spec; ARW is vendor RAW) — explicit test added in Step 2.
- **Synthetic fixture fidelity.** A `Make=SONY` plain TIFF is a valid ARW shell for detection but is not a real ARW. Deeper tag coverage stays gated on local fixtures via the established skip pattern.
- **CAPABILITIES.json validators.** If `tools/generate_capabilities.py` regenerates this file from source-of-truth crate metadata rather than being hand-edited, the manual edit must be reconciled — builder should grep for any drift check before committing.
