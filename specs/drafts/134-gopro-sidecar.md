# Plan #134 (revision 2): Tier S — GoPro `.lrv` proxy + `.thm` thumbnail sidecars

## Problem
Every GoPro card emits a triplet next to each clip — `<basename>.MP4` plus a `<basename>.LRV` low-res proxy (also ISOBMFF) and a `<basename>.THM` JFIF thumbnail. These siblings carry value not as embedded metadata but as *pointers* to cheap-to-stream alternative renditions. Today XIFty discovers no GoPro siblings, so consumers (e.g. kstore creator wedge) cannot ask "is there a proxy I can use?" or "where's the thumbnail?" without re-walking the directory themselves. Issue #134 asks us to surface `proxy.path` / `thumbnail.path` (plus structural dimensions and proxy bitrate) through the existing sidecar framework shipped in #122.

## Approach
Mirror `crates/xifty-sidecar-sony-nrt` exactly — single-purpose crate `xifty-sidecar-gopro` implementing `xifty_sidecar::Sidecar` with `MergePolicy::Complement` and priority `100`. Discovery walks the primary's parent directory and applies two pairing rules:

- **LRV pairing** — GoPro shifts the prefix from `GH`/`GX` (primary) to `GL` (LRV) while preserving the numeric stem (e.g. `GH010024.MP4` → `GL010024.LRV`). A generic `<stem>.LRV` (case-insensitive) fallback covers renamed files.
- **THM pairing** — GoPro keeps the **same prefix and stem** as the primary (e.g. `GH010024.MP4` → `GH010024.THM`, `GX010024.MP4` → `GX010024.THM`). Note: the THM does NOT use the `GL` LRV prefix. A generic `<stem>.THM` (case-insensitive) fallback covers renamed files.

Discovery returns up to two `SidecarRef`s with labels `"lrv"` and `"thm"`. Parse delegates to existing parsers — for `.THM` we call `xifty_container_jpeg::parse_bytes(bytes, 0)` (the same bounds-checked walker used elsewhere) and read width/height from the first SOF segment's payload. For `.LRV` we call `xifty_container_isobmff::parse_bytes(bytes, 0)` and read the `ftyp` major brand, the first video `tkhd` dimensions, and `media_duration_seconds` (already populated by the parser) to derive `proxy.bitrate_bps`. All emitted entries live under namespace `gopro_sidecar` with `Provenance::container = "sidecar"` and `Provenance::path` pointing at the sidecar file. The adapter is registered in `default_sidecar_registry()` in `crates/xifty-cli/src/lib.rs:233-237` alongside `SonyNrtSidecar`. We do NOT add normalize lifts in this plan — entries flow through under the `gopro_sidecar` namespace and surface in `interpreted`/`raw`. Generic `proxy.*` / `thumbnail.*` normalized fields can ride a follow-up issue once a second adapter (Sony THMBNL) exists to validate the shape. Schema stays at `0.1.0` (additive).

## Step-by-step
1. Create the crate skeleton — `crates/xifty-sidecar-gopro/{Cargo.toml,src/lib.rs}` with the namespace constant `"gopro_sidecar"`, container `"sidecar"`, and a `GoProSidecar` unit struct implementing `Sidecar`. Cargo.toml declares `xifty-container-jpeg` and `xifty-container-isobmff` as path deps. Verify: `cargo check -p xifty-sidecar-gopro` succeeds.
2. Implement `discover` — case-insensitively scan `primary.parent()` for two pairings:
   - **LRV**: GoPro-prefixed (`^G[HX](\d+)\.MP4$` → look for `GL<digits>.LRV` with the SAME numeric stem) plus a generic `<stem>.LRV` fallback for renamed primaries.
   - **THM**: same prefix and stem as primary (`<stem>.THM` — works for both GoPro `GH010024.MP4 → GH010024.THM` and the renamed-file generic case in one step; no prefix shift).
   Return up to two `SidecarRef`s with labels `"lrv"` and `"thm"`. Verify: unit tests cover (a) GoPro-prefixed `GH→GL` LRV discovery, (b) GoPro-prefixed `GX→GL` LRV discovery with `GX*.THM` thumb, (c) generic case-insensitive discovery for renamed files, (d) buffer-only returns empty, (e) missing extension is silently skipped.
3. Implement `parse` for `.THM` — when `sidecar.label == "thm"`, call `xifty_container_jpeg::parse_bytes(bytes, 0)`. Walk `container.segments` and find the first `JpegSegment` whose marker satisfies `(marker & 0xF0 == 0xC0) && !matches!(marker, 0xC4 | 0xC8 | 0xCC)` (SOF0/1/2/3/9/10/11/13/14/15, excluding DHT/JPG/DAC). Read dimensions from the segment's `payload` field (which excludes the 2-byte length prefix per `crates/xifty-container-jpeg/src/lib.rs:127`): bytes `[0]` = precision, `[1..3]` = height BE, `[3..5]` = width BE. Bounds-check `payload.len() >= 5` before slicing; on short payload emit `sidecar_parse_error`. Forward any `container.issues` (e.g. `jpeg_segment_length_invalid`) into the sidecar's `Vec<Issue>`. Emit entries `thumbnail.path`, `thumbnail.format` (string `"jfif"`), `thumbnail.size_bytes` (`Integer`), `thumbnail.dimensions.width` and `thumbnail.dimensions.height` (`Integer`). On no-SOF-found emit `sidecar_parse_error` (`Severity::Warning`) but still emit `thumbnail.path` and `thumbnail.size_bytes`. Verify: unit test against a hand-rolled minimal 320×180 SOF0 JFIF byte slice asserts width/height entries; a malformed JFIF surfaces `sidecar_parse_error` and still emits `thumbnail.path`.
4. Implement `parse` for `.LRV` — when `sidecar.label == "lrv"`, call `xifty_container_isobmff::parse_bytes(bytes, 0)` and walk the resulting `IsobmffContainer` for the first video track's `tkhd` dimensions and `ftyp` major brand. Emit `proxy.path`, `proxy.size_bytes`, `proxy.format` (literal `"mp4"`), `proxy.codec` (the major brand string), `proxy.dimensions.width`, `proxy.dimensions.height`. Additionally, read `container.media_duration_seconds: Option<f64>` (already populated by the parser per `crates/xifty-container-isobmff/src/lib.rs:98`). When `Some(dur)` and `dur > 0.0`, emit `proxy.bitrate_bps` as `Integer` computed as `((size_bytes as f64 * 8.0) / dur).round() as i64`. When `None` or `dur <= 0.0`, omit the field silently (no warning — this is benign on container-only fixtures). Verify: unit test against an in-memory minimal LRV bytestring with a known mvhd duration asserts `proxy.codec`, `proxy.dimensions.width`, `proxy.dimensions.height`, and `proxy.bitrate_bps` all land with expected values.
5. Wire into the registry — add the workspace member, extend `crates/xifty-cli/Cargo.toml`, and register `GoProSidecar::new()` in `default_sidecar_registry()` at `crates/xifty-cli/src/lib.rs:235`. Verify: `cargo build -p xifty-cli` succeeds.
6. Build minimal fixtures + integration test — write a small `tests/cli_contract.rs` block (mirroring `sony_nrt_sidecar_synthetic_minimal_fixture_lifts_fields` at line 3169) that loads `fixtures/minimal/gopro/GH010001.MP4` with `extract_with_sidecars`, asserts the interpreted view contains a `gopro_sidecar` entry with `tag_name == "thumbnail.dimensions.width"` carrying `320`, a `proxy.dimensions.width` entry, and a `proxy.bitrate_bps` entry. Add an off-by-default test mirroring `sony_nrt_sidecar_is_off_by_default` (line 3141) that confirms vanilla `extract_path` does not surface `gopro_sidecar` entries. Generate fixtures by either (a) committing tiny hand-built byte sequences or (b) a small build helper similar to the Sony NRT one referenced at `cli_contract.rs:3171`. Verify: `cargo test -p xifty-cli --all-features gopro` passes.
7. Update `CAPABILITIES.json` — add a `gopro` block under `sidecars` with `merge_policy: "complement"`, `discovery: "GH/GX → GL prefix shift for LRV; same-prefix <stem>.THM for thumbnail; generic <stem>.LRV / <stem>.THM fallback"`, and the supported tag list from steps 3-4 (including `proxy.bitrate_bps`). Verify: `cargo test --workspace --all-features` passes.
8. Update `docs/SCHEMA_POLICY.md` — extend the "Sidecar-derived Fields" section to mention `gopro_sidecar` alongside `sony_nrt`. Note that `proxy.*` / `thumbnail.*` are tag names within the `gopro_sidecar` namespace today and may be promoted to generic normalized fields in a follow-up issue.

## Risks
- **JFIF SOF variant coverage** — JPEG SOF markers come in many flavors (SOF0/1/2/3/9/10/11/13/14/15). The dimension byte layout (precision, height BE, width BE at payload offsets 0..5) is shared across all SOF flavors per the JPEG spec, so the generic match pattern in step 3 covers every variant a GoPro Hero camera could emit. We exclude `0xC4` (DHT — Huffman tables), `0xC8` (JPG — reserved), and `0xCC` (DAC — arithmetic coding tables) which share the `0xCx` high nibble but are not start-of-frame.
- **Naming convention drift** — Hero5/6/7/8/9/10/11/12/13 use `GH`/`GX`/`GP`/`GS` prefixes for primary and `GL` for the LRV. The plan handles `GH` and `GX` explicitly per the issue, plus the generic stem fallback. If a future Hero variant uses a different LRV prefix, the generic fallback covers it. THM always shares the primary's prefix so the same-stem rule holds for every variant.
- **Insta snapshot drift** — adding a new sidecar adapter to `default_sidecar_registry()` does not affect existing fixtures (none have a sibling `.LRV` / `.THM`), so the impact should be zero. If a fixture happens to have a `.thm` extension by coincidence, expect drift and review with `cargo insta review` — never blanket-accept (per `.loswf/config.yaml` guardrail).
- **Schema policy** — the plan deliberately scopes lifts to *raw entries under `gopro_sidecar`* without normalize integration. That is additive-only, no `SCHEMA_VERSION` bump (per `docs/SCHEMA_POLICY.md`). Promoting `proxy.*` / `thumbnail.*` to generic normalized fields is a follow-up once a second adapter (Sony THMBNL) exists to validate the shape.
- **Bitrate edge cases** — `media_duration_seconds` may be `None` for malformed LRVs or `Some(0.0)` for zero-length proxies. The implementation must guard with `dur > 0.0` and silently omit `proxy.bitrate_bps` in those cases rather than emitting `0` or panicking on division.
