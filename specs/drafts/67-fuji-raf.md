# Plan #67: RAW — Fuji RAF (custom container + embedded TIFF)

## Problem
Fuji `.RAF` files are a proprietary RAW container that begins with the ASCII magic `FUJIFILMCCD-RAW` at byte 0, followed by a fixed-layout header pointing to a JPEG preview block, a CFA header block, RAW image data, and (most importantly for metadata) an embedded little/big-endian TIFF block that carries EXIF and a Fuji-specific MakerNote. XIFty currently has no detection branch, no `Format::Raf`, no container parser, no Fuji maker-note interpreter, and no CLI wiring for RAF (`crates/xifty-detect/src/lib.rs` lines 4-56 has no RAF arm; `crates/xifty-core/src/lib.rs` lines 8-21 stops at `Ogg`; `crates/xifty-cli/src/lib.rs` `probe_source`/`extract_source` `match format` blocks have no RAF arm). The acceptance criteria require detection by magic, header parsing into container nodes, embedded-TIFF EXIF surfaced via the existing `xifty-meta-exif` decoder, a structurally-parsed Fuji MakerNote, insta snapshots for probe + extract, and `CAPABILITIES.json` reflecting status. Architectural rule: container parsing and metadata interpretation must stay in different crates (SRS §3.1).

## Approach
Mirror the established two-crate split used for Sony (`xifty-container-tiff` + `xifty-meta-sony`): a new container crate `xifty-container-raf` walks the RAF header (magic + magic-string + version + camera id + directory pointers at fixed offsets) and emits `ContainerNode`s plus an `embedded_tiff` slice locator; a new metadata crate `xifty-meta-fuji` consumes the embedded TIFF (post-parse via `xifty-container-tiff::parse_bytes`) and decodes the Fuji MakerNote (`tag 0x927C`, header `b"FUJIFILM"` followed by a little-endian sub-IFD offset). The CLI wires this together exactly like AVIF/HEIF currently dispatches embedded TIFF EXIF in `crates/xifty-cli/src/lib.rs` `isobmff_entries` (lines 1100-1126) and like the JPEG arm at lines 138-160: parse RAF, extract the embedded TIFF payload, hand it to `xifty_container_tiff::parse_bytes(payload, base_offset, "raf_exif")`, then call `decode_from_tiff` (xifty-meta-exif) plus the new `xifty_meta_fuji::decode_from_tiff` for the MakerNote. Detection adds an early branch in `detect()` checking `bytes[0..15] == b"FUJIFILMCCD-RAW"`. Per the issue's plan-ambiguity note (#3), the canonical Fuji MakerNote tag list is TBD; this plan ships a *bounded, structural* MakerNote parse (top-level IFD entries surfaced as raw integers/strings with provenance) and a small initial allowlist of well-understood Fuji tags (e.g. `0x1000 Quality`, `0x1001 Sharpness`, `0x1002 WhiteBalance`, `0x1003 Saturation`, `0x1004 Contrast`, `0x1010 FlashMode`, `0x1011 FlashStrength`, `0x1020 Macro`, `0x1021 FocusMode`, `0x1030 SlowSync`, `0x1031 PictureMode`, `0x1100 ContinuousBracket`, `0x1400 DynamicRange`, `0x1401 FilmMode`) — anything outside the allowlist is emitted with a generic `tag_id = 0x{hex}` and `tag_name = "FujiTag_{hex}"`, matching the "structurally parses" wording in the acceptance criteria.

## New files
- `crates/xifty-container-raf/Cargo.toml` — `xifty-core`, `xifty-source` path deps (mirrors `xifty-container-tiff/Cargo.toml`).
- `crates/xifty-container-raf/src/lib.rs` — public `pub fn parse(source: &SourceBytes) -> Result<RafContainer, XiftyError>` and `pub fn parse_bytes(...)`. `RafContainer` exposes `nodes: Vec<ContainerNode>`, `issues: Vec<Issue>`, `embedded_tiff: Option<RafEmbeddedTiff { offset, length }>`, `jpeg_preview: Option<RafBlock>`, `cfa_header: Option<RafBlock>`, `raw_data: Option<RafBlock>`, plus a helper `pub fn embedded_tiff_slice<'a>(bytes: &'a [u8], container: &RafContainer) -> Option<(u64, &'a [u8])>` mirroring `xifty_container_tiff::xmp_payload`. Header layout parsed: bytes 0..15 magic "FUJIFILMCCD-RAW", 16..19 format version, 20..27 camera id, 28..59 camera string, 60..63 dir-version, 64..83 unknown, 84..87 jpeg image offset, 88..91 jpeg image length, 92..95 cfa-header offset, 96..99 cfa-header length, 100..103 cfa-record offset, 104..107 cfa-record length (big-endian u32s). Embedded TIFF lives inside the JPEG preview block (the preview is a JFIF JPEG with an APP1/EXIF segment) — extract the EXIF APP1 payload via `xifty_container_jpeg::parse_bytes` if available, OR alternatively detect a direct `II*\0`/`MM\0*` marker at the JPEG offset for cameras that ship a bare TIFF block. The parser falls back gracefully (emits `Issue { code: "raf_embedded_tiff_missing", severity: Warning }`) when the embedded TIFF cannot be located, never panics.
- `crates/xifty-container-raf/src/lib.rs` `#[cfg(test)] mod tests` — synthetic-RAF round-trip: build a header in-memory, point JPEG offset to a hand-crafted JFIF+APP1 EXIF block, assert `embedded_tiff_slice` returns the inner TIFF bytes; bounds tests for truncated header, magic mismatch, out-of-bounds offsets.
- `crates/xifty-meta-fuji/Cargo.toml` — `xifty-core`, `xifty-source`, `xifty-container-tiff` path deps (mirrors `xifty-meta-sony/Cargo.toml`).

## Step-by-step
1. **Add `Format::Raf`** in `xifty-core` and its `as_str` arm — verifiable by `cargo build -p xifty-core`.
2. **Add detection branch** in `xifty-detect` for the 15-byte magic; extend `detects_formats` test — verifiable by `cargo test -p xifty-detect`.
3. **Create `xifty-container-raf`** crate skeleton + Cargo.toml; register in workspace `Cargo.toml` — verifiable by `cargo build -p xifty-container-raf`.
4. **Implement RAF header walker** producing `ContainerNode`s (`raf`, `raf_jpeg_preview`, `raf_cfa_header`, `raf_raw_data`, `raf_embedded_tiff`) with byte-accurate `offset_start`/`offset_end`; emit defensive issues for truncation/bad offsets — verifiable by unit tests on a synthetic header.
5. **Implement embedded-TIFF locator** (`embedded_tiff_slice`) that finds the EXIF APP1 inside the preview JPEG (or a bare TIFF) — verifiable by unit test that hands the function a hand-crafted preview and asserts the returned `(offset, &[u8])` starts with `II*\0`/`MM\0*`.
6. **Create `xifty-meta-fuji` crate** skeleton + Cargo.toml; register in workspace — verifiable by `cargo build -p xifty-meta-fuji`.
7. **Implement Fuji MakerNote parse** with the Sony-shaped `decode_from_tiff(bytes, base, container, tiff, exif_entries)` signature; allowlist mapping for ~14 well-understood tags, structural fall-through for the rest — verifiable by unit tests asserting two allowlisted tags + one generic `FujiTag_xxxx`.
8. **Wire CLI `probe_source` and `extract_source`** for `Format::Raf`: parse RAF, parse embedded TIFF via `xifty_container_tiff::parse_bytes(payload, offset, "raf_exif")`, run `decode_from_tiff` (exif) + `decode_apple_from_tiff` (no-op for Fuji but keeps shape consistent — review whether to skip), then `xifty_meta_fuji::decode_from_tiff`. Add cli Cargo.toml deps. Verifiable by `cargo build -p xifty-cli`.
9. **Add `fixtures/minimal/happy.raf`** synthetic file (header + JPEG preview with APP1/EXIF + MakerNote) — verifiable by `xifty_cli::probe_path` returning `detected_format = "raf"` in an ad-hoc test.
10. **Add insta snapshot tests** in `crates/xifty-cli/tests/cli_contract.rs`: `probe_snapshot_happy_raf`, `extract_snapshot_happy_raf_normalized`, `extract_snapshot_happy_raf_interpreted` — verifiable via `cargo insta review` then `cargo test -p xifty-cli`.
11. **Update `CAPABILITIES.json`** with new `raf` container entry and new `fuji` namespace entry — verifiable by `cargo test --workspace --all-features` (the hygiene workflow validates this artifact; locally, the test suite will remain green).
12. **Run validation gates** — `cargo fmt --all -- --check`, `cargo test --workspace --all-features`, `cargo test -p xifty-ffi --all-features`.

## Risks
- **Synthetic fixture authenticity**: a hand-crafted minimal RAF may not exercise the same code paths a real Fuji file does. Mitigation: build the fixture so its embedded JPEG actually carries an APP1/EXIF segment matching real Fuji structure (`II*\0` at the standard JPEG-EXIF offset), and document the byte layout in `fixtures/minimal/README.md`.
- **MakerNote tag list TBD (issue plan-ambiguity #3)**: the allowlist of ~14 tags is a deliberate first cut; values for enumerated tags (Quality, PictureMode etc.) are decoded as raw integers in this M-sized task, and a follow-up can layer enum mapping on top without container changes.
- **`Format::Raf` is a new public enum variant** in `xifty-core` and serializes as `"raf"` (snake_case). Any downstream JSON consumer that exhaustively matches the format string will see a new value — schema is still additive, so this is non-breaking, but call it out in the PR description.
- **Embedded-TIFF location varies**: some Fuji bodies put EXIF inside the JPEG preview's APP1, others put a bare TIFF block elsewhere referenced by the directory. The parser must try both paths and emit a warning issue (not an error) when neither resolves, so probe still returns container nodes for the rest of the layout.
- **No JPEG-specific dep currently in `xifty-container-raf`**: if APP1/EXIF extraction needs `xifty-container-jpeg`, add that path-dep; otherwise inline a small `find_app1_exif(bytes) -> Option<(u64, &[u8])>` to keep the container crate's footprint tight.
- **Cross-crate boundary**: the Fuji MakerNote decoder lives in `xifty-meta-fuji`, not in `xifty-container-raf` — preserves the SRS §3.1 invariant. The CLI is the only place that combines them, exactly like Sony today.
