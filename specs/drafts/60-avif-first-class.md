# Plan #60: AVIF — promote to first-class `Format::Avif` + colr/cicp/pixi surfacing (v2)

## Problem
AVIF still images and image sequences are currently lumped under `Format::Heif` because `crates/xifty-detect/src/lib.rs` treats the `avif`/`avis` ISOBMFF brands as HEIF via `heif_brand()` at lines 37-58. This hides AVIF as its own capability, blocks HDR color surfacing (nclx/cicp/pixi), and prevents AVIS (sequence) duration from being reported. Issue #60 asks for a first-class `Format::Avif` variant with correct detection ordering, plus `colr (nclx/prof)`, `cicp`, and `pixi` surfaced into normalized HDR color fields, while keeping existing HEIF behavior and tests green. This revision (v2) addresses the five plan-reviewer gaps: (1) ipco-inner dispatch precision, (2) AVIF EXIF path, (3) cross-crate compile atomicity, (4) container-label consistency, and (5) the `major=heic compat=[avif]` ordering test.

## Approach
Add `Format::Avif` to `xifty-core`, then split detection so the AVIF brand check runs BEFORE the HEIF check (otherwise `avif`/`avis` would be swallowed by `heif_brand`, which still lists those brands at `xifty-detect/src/lib.rs:56`). Route `Format::Avif` through the existing ISOBMFF parser (same transport as HEIF, MP4, MOV) and reuse the existing `container = "isobmff"` label — AVIF is ISOBMFF transport, so consistency with HEIF/MP4/MOV beats introducing a one-off label (plan-reviewer gap #4 resolved toward option (a): keep `"isobmff"`, distinguish by `detected_format`). In `xifty-container-isobmff`, extend `parse_colr` at line 1359 to also surface nclx (primaries/transfer/matrix/range) as typed payloads, and add `parse_cicp` and `parse_pixi` arms INSIDE `parse_children` at the same match level as the existing `b"colr"` arm at line 437 (i.e., siblings of `b"colr"` within the recursive walk that processes `ipco`'s children — NOT at the outer `b"ipco"` arm; plan-reviewer gap #1 resolved). Step 1 and step 5 (cli arm) land atomically in the same commit so the workspace always compiles (plan-reviewer gap #3 resolved toward option (b)). The AVIF EXIF path reuses `heif_exif_tiff` because AVIF shares the HEIC 4-byte ItemOffset preamble convention (plan-reviewer gap #2 resolved: extend the gate at `xifty-cli/src/lib.rs:692` to `format_name == "heif" || format_name == "avif"`). In `xifty-normalize`, add `color.primaries`, `color.transfer`, `color.matrix`, `color.range`, and `color.bit_depth` with precedence cicp > pixi > colr/nclx. New insta fixtures for still AVIF and AVIS sequence are generated via `tools/generate_fixtures.py` mirroring `build_heif*`.

## Risks
- **Container-label policy (gap #4).** Plan keeps `container = "isobmff"` for AVIF (consistent with HEIF/MP4/MOV). Any downstream consumer that demanded a distinct `"avif"` container label must instead branch on `detected_format`. This matches the existing pattern (HEIF and MP4 both use `"isobmff"`).
- **AVIF EXIF via HEIC preamble (gap #2).** AVIF EXIF is specified to use the same ItemData 4-byte `tiff_header_offset` prefix convention as HEIC; extending the gate is the correct fix. Risk: a non-conforming encoder emits raw TIFF without the preamble. Mitigation: the gate's `else if` branch already falls through to raw `II`/`MM` detection when `heif_exif_tiff` returns `None`, so a malformed AVIF still degrades gracefully.
- **Compile-window atomicity (gap #3).** Step 1 is explicitly atomic (core variant + both cli arms in one commit). Any builder shortcut that skips the cli arm will break `cargo check --workspace` immediately.
- **Ordering edge case (gap #5).** The new test codifies "AVIF wins on any AVIF brand". If a real-world producer emits `heic` major with `avif` compat to signal dual-decode capability, those files now route to `Format::Avif` — intentional and aligned with AVIF spec expectations (AVIF decoders must accept such files, HEIF decoders may not).
- **ipco-inner dispatch (gap #1).** `cicp`/`pixi` arms go at the same level as `b"colr"` at line 437 (inside the children walk). A builder who places them at the outer `b"ipco"` arm would silently never parse them; the plan explicitly calls this out and the unit tests on synthetic ipco payloads will catch the mistake.
- **Snapshot discipline.** Workspace policy forbids blanket `cargo insta accept`; all new snapshots must go through `cargo insta review`.
- **FFI surface.** `xifty-ffi` returns JSON strings for format; adding `Format::Avif` is source-compatible (new string value, no signature change). No `FFI_CONTRACT.md` update needed.
- **`heif_brand` in `xifty-container-isobmff`.** The parser-level brand list at `crates/xifty-container-isobmff/src/lib.rs:1466-1471` still accepts `avif`/`avis` — that is correct (AVIF IS ISOBMFF) and must remain unchanged; only `xifty-detect::heif_brand` loses those entries.
